Desarrollo Orientado a Objetos

De “guardar datos” a diseñar objetos que protegen sus propias reglas.

Hoy conectamos Java con una idea fundamental de la ingeniería de software: un objeto no debería ser solo un conjunto de variables. También debe proteger aquello que sabemos que siempre debe ser cierto.

01 · La idea central

Primero: entender el problema en lenguaje simple

Un personaje tiene datos. Algunos pueden cambiar. Pero no cualquier cambio debería estar permitido.

Por ejemplo: la vida de un personaje puede cambiar, pero su vida no debería quedar en −20.

Cuando una clase protege estas condiciones, estamos empezando a diseñar objetos con responsabilidades propias.

02 · Abstracción

¿Qué significa abstraer?

Abstraer es quedarse con lo importante para el problema y ocultar detalles que no necesitamos manipular directamente.

En el mundo real

Sabemos que un personaje tiene nombre, vida y puede recibir ataques. No necesitamos modelar cada molécula de su cuerpo.

En el programa

La clase Personaje representa aquello que nuestro sistema necesita conocer y hacer con un personaje.

Idea ingenieril: la abstracción reduce complejidad al trabajar con modelos relevantes para el dominio.

03 · Encapsulamiento

Encapsular es controlar el acceso

No significa simplemente “poner private”. Significa proteger el estado interno de un objeto y definir cómo puede ser consultado o modificado.

private int vida;

Desde fuera de Personaje, no podemos modificar directamente vida.

La clase se convierte en la responsable de decidir qué cambios son válidos.

04 · Public vs. private

¿Por qué importa?

Acceso directo

personaje.vida = -20;
El código externo puede romper las reglas del personaje.

Acceso controlado

personaje.setVida(-20);
La clase puede validar el valor antes de aceptarlo.

El objetivo no es impedir cambios. Es impedir cambios inválidos.

05 · Getters y setters

Una puerta de entrada al estado interno

public void setVida(int vida) {
    if (vida < 0) {
        this.vida = 0;
    } else {
        this.vida = vida;
    }
}

public int getVida() {
    return vida;
}

Getter: consulta. Setter: propone una modificación. La clase decide si esa modificación es válida.

06 · this

¿Qué significa this.vida?

this representa al objeto actual. Permite distinguir el atributo del objeto de un parámetro local con el mismo nombre.

public void setVida(int vida) {
    if (vida < 0) {
        this.vida = 0;
    } else {
        this.vida = vida;
    }
}

public int getVida() {
    return vida;
}

“La vida de este personaje recibe el valor de vida que llegó al método”.

07 · Reglas del dominio

La vida nunca puede ser negativa.

Esta no es una regla de Java. Es una regla de nuestro mundo.

Regla del dominio

Un personaje no puede tener menos de 0 puntos de vida.

Responsabilidad

El objeto Personaje debe proteger esa regla, independientemente de quién intente cambiar su vida.

Esto es una primera aproximación a la idea de invariante: una condición que debe mantenerse válida durante la vida del objeto.

08 · Comportamiento

Un objeto no solo tiene datos.

También tiene comportamientos relacionados con esos datos.

personaje.recibirAtaque(25);

La operación tiene más sentido que hacer desde Main algo como:

personaje.vida = personaje.vida - 25;

El primer enfoque entrega responsabilidad al objeto. El segundo expone demasiado de su implementación.

09 · Scanner

Entrada de datos desde la consola

Scanner scanner = new Scanner(System.in);

String nombre = scanner.nextLine();

Scanner permite leer información ingresada por el usuario. En nuestro caso, usamos nextLine() para obtener una línea completa como String.

La entrada del usuario es texto. Si necesitamos un número, debemos convertirlo.

10 · Parseo

De texto a número

String texto = scanner.nextLine();
int vida = Integer.parseInt(texto);

nextLine() entrega un String. Integer.parseInt() intenta convertir ese texto a un int.

Ejemplo: "120" → 120. Si el texto no representa un entero válido, la conversión puede producir una excepción.

Nota conceptual: parsear no es lo mismo que hacer un cast. Aquí estamos interpretando texto para producir otro tipo.

11 · While

Repetir mientras una condición sea verdadera

boolean mantener_menu = true;

while (mantener_menu) {
    // mostrar y procesar menú
}

El menú continúa ejecutándose mientras mantener_menu sea true. Cuando pasa a false, el ciclo termina.

Patrón útil: una variable de control expresa claramente cuándo debe continuar una interacción.

12 · switch

Elegir entre alternativas

switch (opcion_menu) {
    case "1":
        // crear personaje
        break;

    case "2":
        // ver personaje
        break;

    case "3":
        // cerrar
        break;

    default:
        // opción no reconocida
}

switch permite expresar de manera clara que una entrada puede llevar a diferentes caminos.

14 · Mirada ingenieril

¿Qué problema estamos resolviendo realmente?

Estamos reduciendo la cantidad de lugares del programa que necesitan conocer cómo funciona internamente un personaje.

Antes: cualquier parte podría modificar directamente los datos.

Después: el objeto ofrece operaciones y decide cómo mantener sus reglas.

Esto prepara el camino hacia principios de diseño más grandes: bajo acoplamiento, alta cohesión, responsabilidades claras y polimorfismo.

15 · Ejercicio 1
01

El oro de Poniente

Nuestro personaje ya tiene nombre, apellido y vida. Ahora necesitamos incorporar el oro que utilizará durante su aventura.

Agrega la cantidad de oro inicial al crear el personaje y permite visualizarla junto con sus demás datos.

Durante las pruebas descubrimos un problema: actualmente es posible asignarle al personaje una cantidad negativa de oro. Un personaje no puede tener menos de 0 monedas.

Corrige el diseño para garantizar que esta regla siempre se cumpla, incluso cuando se intente modificar el oro desde otra parte del programa.

Finalmente, agrega una operación que permita gastar una determinada cantidad de oro. El personaje solo podrá realizar el gasto si posee suficientes monedas.

16 · Ejercicio 2
02

La batalla por Poniente

Nuestro personaje necesita una nueva característica: la fuerza. Esta determinará cuánto daño puede realizar durante un combate.

Agrega la fuerza al personaje y permite establecerla y visualizarla durante la creación.

Durante las pruebas descubrimos que es posible asignarle valores inválidos, como una fuerza negativa. La fuerza de un personaje nunca puede ser menor que 0.

Corrige el diseño para garantizar esta regla.

Ahora los personajes deben poder enfrentarse. Un personaje debe poder atacar a otro utilizando su fuerza, y el personaje atacado debe actualizar correctamente su vida y su estado.

Un personaje que haya muerto no puede continuar recibiendo ataques.

La batalla debe poder realizarse entre dos objetos Personaje, sin que Main tenga que modificar directamente sus vidas.

17 · Ejercicio 3
03

Las casas de Poniente

Los personajes ahora pertenecen a una casa:

STARKLANNISTERTARGARYENBARATHEONGREYJOY

La casa debe formar parte de los datos del personaje y debe poder visualizarse junto con el resto de su información.

Cada casa posee una característica especial durante el combate: STARK puede resistir un ataque; LANNISTER obtiene oro al derrotar; TARGARYEN aumenta su ataque con poca vida; BARATHEON realiza más daño con mucha vida; GREYJOY puede esquivar.

Implementa estas reglas en el sistema de combate. Todos los personajes deben seguir utilizando los mismos comportamientos de combate, pero su casa debe influir en la forma en que estos comportamientos funcionan.

Finalmente, inventa una habilidad adicional para una de las casas y agrégala al juego.

18 · Cierre

La pregunta importante no es “¿cómo lo programo?”

Primero preguntamos: ¿qué cosas son ciertas en nuestro mundo?, ¿qué cosas puede hacer cada objeto?, ¿qué cosas no deberían poder hacer otros objetos?

Después elegimos las herramientas de Java para expresar ese diseño.

Programar orientado a objetos no es solamente crear clases. Es decidir qué responsabilidades pertenece a cada objeto y proteger las reglas que hacen válido su estado.
